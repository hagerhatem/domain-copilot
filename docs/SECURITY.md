# Security Controls

This document maps every security control actually implemented in this codebase
to the specific threat it addresses, per project brief Section 7's OWASP Web Top
10 / OWASP LLM Top 10 requirement. It is organized by threat category, not by
prompt/phase number, so a reviewer can check coverage threat-by-threat.

**Honesty note (project brief Section 10):** this table only lists controls that
exist in the code today. Known gaps are called out explicitly in a separate
section at the end — they are not hidden, and they are not implemented here
"for show."

## OWASP Web Top 10

| Threat | Control | Where Implemented | How Verified |
|---|---|---|---|
| **A01: Broken Access Control** — a Clinician viewing/approving/rejecting/cancelling another user's run (BOLA/IDOR) | `ApprovalWorkflowUseCase.ApplyAsync` checks `run.InitiatedByUserId == callerUserId` (or caller has the `Admin` role) *before* reading draft text or mutating any state; the same ownership check is applied in `RunsController.Stream` (against `ClinicalCase.CreatedByUserId`) and `RunCancellationRegistry.TryCancel` (against the run's registered owner) | `DomainCopilot.Application/Orchestration/ApprovalWorkflowUseCase.cs`, `DomainCopilot.Api/Controllers/ApprovalController.cs`, `DomainCopilot.Api/Controllers/RunsController.cs`, `DomainCopilot.Api/Streaming/RunCancellationRegistry.cs` | `AuthorizationTests.cs` (integration, real HTTP pipeline) proves cross-role rejection (403 for non-Clinician on `/runs/{id}/approve`); ownership-specific unit tests for `ApprovalWorkflowUseCase`/`RunsController` are a documented follow-up (see Gaps) |

| **A07** — user enumeration via login response differences | `/auth/login` returns the identical `401 Unauthorized` (no distinguishing message) for "no such user," "user is locked out," and "wrong password" | `Program.cs` (`/auth/login` handler) | Manual: comparing response bodies/status codes for the three cases shows no observable difference |

## OWASP LLM Top 10

| Threat | Control | Where Implemented | How Verified |
|---|---|---|---|
| **LLM01: Prompt Injection** (indirect, via ingested/retrieved documents) — malicious instructions embedded in a guideline document attempting to alter agent behavior | Two-layered defense: (1) `SafetyCheckerAgent` has **no `ILLMProvider` dependency at all** — retrieved content can only ever become inert `SafetyWarning` data (fixed `Info` severity), never an executed instruction, because there is no LLM call in its path for an injected instruction to hijack. (2) `DocumentationDrafterAgent`'s `CompletionRequest` uses real privilege separation: fixed instructions live in a `system` message containing zero retrieved content; all retrieved excerpts/warnings are confined to a `<untrusted_retrieved_content>`-delimited section of the `user` message, with an explicit instruction not to treat its contents as commands | `DomainCopilot.Infrastructure/Agents/SafetyCheckerAgent.cs`, `DomainCopilot.Infrastructure/Agents/DocumentationDrafterAgent.cs` (`SystemInstructions`, `BuildUserMessage`) | Three synthetic injection payloads under `src/seed-data/injection-tests/` (silence-a-warning, fabricate-dosage-and-break-format, forge-approval); `PromptInjectionTests.cs` proves (a) the deterministic safety finding is unaffected by an injected "ignore this warning" instruction, (b) each payload is structurally confined to the user message's delimited block and absent from the system message, and (c) even a worst-case fully-compliant mocked model response cannot grant approval or skip the human approval gate, since that gate is `AgentRun`'s own state machine and is never reachable from this agent. **Scope limit, stated honestly:** these tests prove the request *structure* enforces separation and that agent-level code grants no extra privilege from injected text; they cannot prove a specific real model will refuse to *comply in its own output* — that depends on the model. |
| **LLM02: Insecure Output Handling** — blindly trusting a model's claim about which tool it wants to call | `OllamaLLMProvider.CallToolAsync` validates the model-reported `ToolName` against `request.Tools` (the caller-declared allow-list) before returning it as a tool call; an unrecognized tool name is downgraded to plain text output instead of being passed up the chain | `DomainCopilot.Infrastructure/Llm/OllamaLLMProvider.cs` | Code review — `Any(t => t.Name == toolCall.ToolName)` check added ahead of returning a `ToolCallResponse` with tool calls populated. **Gap:** `ToolDefinition.JsonSchema` is currently a descriptive string only, not a schema validated against `ArgumentsJson` — see Gaps section |
| **LLM04: Model Denial of Service** — unbounded LLM cost per user | Twist T3 Cost Governor: pre-flight token estimate checked and reserved against a per-user `TokenBudget` before any agent runs (`RunClinicalWorkflowUseCase`), with a true hard cut-off (not just a UI warning) enforced via an atomic DB transaction (`SqlTokenBudgetService.HasSufficientBudgetAsync`, `SELECT ... WITH (UPDLOCK, ROWLOCK)`) | `DomainCopilot.Application/Orchestration/RunClinicalWorkflowUseCase.cs`, `DomainCopilot.Infrastructure/CostGovernor/SqlTokenBudgetService.cs` | Same test as A04 above (`RunClinicalWorkflowUseCaseTests`) |
| **LLM06: Sensitive Information Disclosure** — real patient data entering the system/LLM prompts | `ClinicalCase.Create` throws if `isSyntheticData` is ever passed as `false` — real patient data cannot be constructed as a valid `ClinicalCase` at the domain-model level, not just by policy/documentation | `DomainCopilot.Domain/Entities/ClinicalCase.cs` | Domain-level guard clause; a dedicated unit test asserting the throw is a documented follow-up (see Gaps) |
| **LLM08: Excessive Agency** — an agent's tool/LLM output directly finalizing a clinically significant decision with no human check | `DocumentationDrafterAgent`'s `DraftClinicalNote` output is never self-finalizing: `AgentRun.RequestApproval()` → `ApplyApprovalDecision()` requires a real, authenticated Clinician HTTP request via `ApprovalWorkflowUseCase`, a completely separate code path this agent has no access to and never calls. ## Known Gaps (stated honestly, not hidden)

These are real, current limitations — listed here per the project brief's explicit
preference for candor about cuts over an inflated completeness claim:

1. **`ToolDefinition.JsonSchema` is descriptive text, not an enforced schema.** The allow-list check (LLM02, above) prevents an unrecognized *tool name* from being executed, but `ToolCall.ArgumentsJson` itself is never validated against a real JSON Schema before use. Currently low-risk because no agent in this codebase actually consumes `ArgumentsJson` yet (`SafetyCheckerAgent` and `GuidelineResearcherAgent` call their tools directly in code, not via the LLM tool-calling path) — but this must be closed with a real schema-validation library (e.g. `JsonSchema.Net`) before any agent starts consuming model-supplied arguments.
2. **No dedicated unit test for JWT signature tampering** (A08). Covered only indirectly by `AuthorizationTests`' unauthenticated-request case.
3. **No dedicated unit test asserting `ClinicalCase.Create(..., isSyntheticData: false)` throws** (LLM06). The guard clause exists and is exercised implicitly by every other `ClinicalCase` test using the default `true`, but no test targets the `false` path directly.
4. **Ownership-check unit tests for `ApprovalWorkflowUseCase`/`RunsController` are integration-level only** (via `AuthorizationTests`' role check), not unit-level for the specific same-role-different-owner case (e.g. two different Clinician accounts, one trying to approve the other's run). The code path exists and is reviewed, but lacks a targeted automated test.
5. **CSP is a single blanket `default-src 'self'`**, not tuned per-route; if a future Swagger UI or admin dashboard needs inline scripts/styles, this will need route-specific relaxation rather than a global loosening.
6. **Rate limiting is in-memory, per-instance.** If the API is ever horizontally scaled to multiple instances, the fixed-window limiters (both global and `"login"`) do not share state across instances — a distributed store (e.g. Redis-backed limiter) would be needed for the limits to hold cluster-wide.
7. **OWASP LLM03 (Training Data Poisoning) and LLM05 (Supply Chain Vulnerabilities)** are not covered in this document. LLM03 does not apply (no model training/fine-tuning occurs anywhere in this project). LLM05 (dependency/secret scanning in CI) is tracked as a separate CI/CD deliverable, not an application-code control, and is documented under Section 7's CI requirements rather than here.
